# i18n — Rules & Architecture

Two languages: English (`en`) and Chinese (`zh`). System designed to extend to more languages.

## Quick Rules

**Adding UI text:**
1. Add key + English value to `assets/locales/en.json` ui section
2. Add same key + Chinese value to `assets/locales/zh.json` ui section
3. Add key to `UiKey` union in `src/lib/t.ts`
4. Use `t('key')` in React components, `makeT(language)('key')` in pure functions
5. Run `npm run i18n:check` before committing

**Never:**
- Hardcode `zh ? '中文' : 'English'` for UI labels — use `t(key)`
- Create `{ en: 'foo', zh: '…' }` objects for UI text — use `t(key)`
- Call `useT()` inside nested functions or callbacks — call it at component top
- Add a near-duplicate key before searching for an existing reusable key

---

## File Layout

```
assets/locales/
  en.json          ← UI strings (all keys under "ui": {...})
  zh.json          ← UI strings (matching keys)
  en.jinxes.json   ← Jinx text (EN). Separate to keep locale files focused.
  zh.jinxes.json   ← Jinx text (ZH). Loaded by catalog.ts alongside main locale.
  terminology.json ← Human-readable BOTC glossary + validator guardrails.
```

**Not yet extracted (future work):**
- `src/utils/logI18n.ts` — game-log narrative phrases. Standalone sub-system, see §Game Log below.
- `src/components/Tutorial/tutorialSteps.ts` — tutorial content. Long-form, separate concern.

## API

### React components
```tsx
import { useT } from '../context/I18nContext'

function MyComponent() {
  const { t, tpl, language } = useT()
  return <Button>{t('save')}</Button>
}
```

### Pure functions / non-hook contexts
```ts
import { makeT, makeTpl } from '../lib/t'

function buildText(language: Language) {
  const t = makeT(language)
  const tpl = makeTpl(language)
  return t('save') + ' — ' + tpl('day_n', 3)
}
```

### Templates (strings with placeholders)
```ts
// en.json: "day_n": "Day {0}"
// zh.json: "day_n": "第 {0} 天"
tpl('day_n', dayNumber)   // → "Day 3" | "第 3 天"

// en.json: "showing_n_of_m": "Showing {0} of {1}"
tpl('showing_n_of_m', 5, 100)  // → "Showing 5 of 100"
```

## When NOT to use t()

**Data fields** — character names, script titles have `nameEn`/`nameZh` or `title`/`titleZh` properties on the data object. Use those directly:
```ts
// ✅ Correct — selecting localized data field
const name = language === 'zh' ? char.nameZh : char.nameEn

// ✅ Correct — catalog utility already handles language
getDisplayName(charId, language)

// ❌ Wrong — 'zh' is data logic, not UI string
const lang = t('zh')
```

**Game-log phrases** — go into `logI18n.ts`, not locale JSON (see §Game Log).

## Adding a New UI Key

1. Pick a `snake_case` key name. Short, descriptive. Examples: `save`, `delete_record`, `connection_failed`.

   Before adding the key, run `rg "existing text|similar_key" assets/locales src` and prefer a shared key when the concept already exists.

2. Add to **both** locale files (same line number for easy diff):
   ```json
   // en.json
   "my_new_key": "My English text",

   // zh.json
   "my_new_key": "我的中文文字",
   ```

3. Add to `UiKey` in `src/lib/t.ts` — append to the end of the union (line before `TplKey`):
   ```ts
   | 'my_new_key'
   ```

4. Use in code: `t('my_new_key')`.

### Adding a template key

Same as above but:
- Use `{0}`, `{1}`, … for positional args in the string value
- Add to `TplKey` (not `UiKey`) in `src/lib/t.ts`
- Use `tpl('my_key', arg0, arg1)` in code

## Translation Notes

For keys needing translator context, add a `// NOTE:` comment near the key in the locale JSON, or maintain a companion `assets/locales/translation-notes.md`:

```
# Translation Notes

## connection_failed
Shown when Google Drive OAuth fails. Followed by the actual error message string.
Keep short — fits in an Alert banner.

## exile_2
" [exile]" — note the leading space. Used inline after a seat number: "#3 [exile]".
```

## BOTC Terminology

Canonical BOTC terms live in `assets/locales/terminology.json`. Keep that file aligned with UI copy whenever adding or changing game-specific language.

| Concept | EN | ZH | Notes |
|---------|----|----|-------|
| Role power | ability | 能力 | Use for character powers. Avoid "skill" unless referring to AI tool skills or internal type names. |
| Demon Bluffs | Demon Bluffs | 恶魔伪装 | Use for the three out-of-play characters shown to the demon. |
| Script | script | 剧本 | Use for BOTC script sheets and script data. Avoid user-facing `脚本`. |
| Storyteller | Storyteller | 说书人 | Use for the game runner. |
| Nomination passed | Nomination Passed | 提名通过 | Use when a nomination reaches the vote threshold. |
| Jinx | jinx | 相克规则 | Use for special interactions between character pairs. |

`npm run i18n:check` reads the glossary and warns on configured deprecated terms such as `恶魔虚张`, `脚本信息`, `影响setup`, or `Nomination Succeed`.

## Reuse & Duplication Rules

- Use canonical concept keys for reusable labels (`save`, `cancel`, `characters`, `script`, `demon_bluffs`).
- Use context-specific keys only when the same English text needs different Chinese text, grammar, casing, or tooltip context.
- Use suffix keys only for grammar/count contexts, for example `characters_suffix`.
- Do not introduce new `_2` keys. Existing `_2` keys are legacy migration artifacts listed in `terminology.json`; replace them gradually with semantic names.
- Avoid generic keys with context-specific meanings. If a label says `Next` in a wizard, use a wizard-specific key if another screen needs `Next day`.

Gradual duplicate cleanup:
1. Define or choose a canonical key.
2. Update all usages that have the same UI meaning.
3. Keep any old key only while `rg "t\\('old_key'\\)" src` shows active usage.
4. Remove the old key from both locale files and from `UiKey`.
5. Run `npm run i18n:check:strict`.

## Game Log Phrases (`logI18n.ts`)

`src/utils/logI18n.ts` is a self-contained sub-system for narrative event-log strings (e.g. "#3 died", "Nomination failed: #1 → #5"). These differ from UI labels:
- Embedded in longer sentences via string concatenation
- Some have seat numbers injected
- Not shown in UI controls — only in log output/export

**Rules for game-log strings:**
- New narrative phrases → add to `PHRASES` in `logI18n.ts`
- Compound strings → add a helper to `logDetail` in the same file
- Do not use `t()` for these — use `logPhrase(lang, key)` or `logDetail.xxx(lang, ...)`

**Future:** PHRASES could be extracted to `assets/locales/en.phrases.json` / `zh.phrases.json` using the same sidecar pattern as jinxes. Catalog.ts would load them and inject into `LocaleData`. This is not done yet to avoid disrupting log tests.

## Adding a New Language

1. Copy `assets/locales/en.json` → `assets/locales/<lang>.json`. Translate all values.
2. Copy `assets/locales/en.jinxes.json` → `assets/locales/<lang>.jinxes.json`. Translate.
3. Extend `Language` type in `src/types.ts`:
   ```ts
   export type Language = 'en' | 'zh' | '<lang>'
   ```
4. Add import + entry in `catalog.ts`:
   ```ts
   import langLocale from '../assets/locales/<lang>.json'
   import langJinxLocale from '../assets/locales/<lang>.jinxes.json'

   export const locales: Record<Language, LocaleData> = {
     en: { ...enLocale, jinxes: enJinxLocale },
     zh: { ...zhLocale, jinxes: zhJinxLocale },
     <lang>: { ...<lang>Locale, jinxes: <lang>JinxLocale },
   }
   ```
5. Add language toggle option in the UI (Settings tab).
6. Update `logI18n.ts` PHRASES to include `<lang>` entries.

## Key Naming Conventions

| Pattern | Use for |
|---------|---------|
| `snake_case` | All keys |
| `action_noun` | Buttons: `save_record`, `delete_folder` |
| `noun` | Labels: `title`, `language`, `script` |
| `no_xxx` | Empty states: `no_records_yet`, `no_scripts` |
| `confirm_xxx` | Confirmation prompts: `confirm_delete` |
| `tab_desc_xxx` | Tab tooltip descriptions |
| `log_xxx` | (Reserved for future game log phrase migration) |

**Avoid:**
- `_2` suffix (migration artifact — consolidate instead)
- Duplicate keys with same value — one canonical key per concept
- Encoding language in the key name (`key_zh`, `key_en`)
